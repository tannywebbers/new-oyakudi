REBUILD PROMPT — "Decompiled APK -> Branded, Function-Complete Android App"
Reusable blueprint for converting ANY decompiled APK into a new Android app that
keeps the decompiled app's original theme/layouts, adopts the decompiled app's
app name + package + (bumped) version, and implements the full SapaClear + PixKudi
feature/function set (login/OTP/app-name gate, announcements modal, news ticker,
withdraw + ledger, and the repayment + payment-webhook flow).

1. NON-NEGOTIABLE RULES
================================================================================

1.1 The new app's VISUALS come from the decompiled APK. Extract its theme tokens
    and component styling and reproduce them faithfully. The decompiled app is
    XML-View based; you are rebuilding the SAME design in Jetpack Compose.
    Match colors, corner radii, spacing, fonts, gradients, icons, and screen
    composition as closely as possible.

1.2 The new app's FUNCTIONS come from SapaClear/PixKudi. Keep the data layer
    (Supabase + Room + repositories + view models) behavior identical. Do not
    change network paths, table names, or login semantics.

1.3 The decompiled APK is NOT buildable as Java. Treat:
      - apktool output (smali + res)  -> authoritative for resources/layouts.
      - jadx output (Java)            -> readable reference only; may not compile.
    You are WRITING a fresh Kotlin/Compose project, not rebuilding smali.

1.4 Do NOT use a generic Material palette for branding. Use the decompiled
    app's palette (mapped to semantic names: primary, primarySoft, accent,
    textMain, textMuted, textHint, divider, fieldBg, card gradients, tab
    active/inactive, status/danger, and well/panel tints). Keep raw hex values
    from the decompiled app.

1.5 Preserve the exact resource IDENTIFIERS from the decompiled app where you
    port resources manually (drawables, string names). WARNING: when doing
    project-wide string replacement, PowerShell -replace is CASE-INSENSITIVE
    and will corrupt lowercase resource names (e.g. img_appname_logo ->
    img_AppName_logo, which is invalid). Use case-sensitive replacement only.

1.6 Never print or commit secrets. The Supabase key here is a publishable/anon
    key (safe for clients); do not add a service-role key to the app.

1.7 Do NOT build the APK or run smoke tests unless explicitly asked. When asked,
    follow the toolchain in Section 6.

1.8 Keep <NEW_PROJECT_DIR> clean: exclude .gradle/, build/, .git/, *.apk from any
    copy operations.

1.9 APP NAME + PACKAGE + VERSION come from the DECOMPILED APK (never invented):
      - App name / label: use the decompiled app's user-facing brand as <APPNAME>
        (from AndroidManifest.xml android:label and res/values strings). Set the
        new project's res/values app_name to that same name.
      - applicationId (the INSTALLED package name): copy the decompiled apk's
        AndroidManifest.xml android:package attribute verbatim
        (for PixKudi that is "app.pixkudi.service.ng"). Do NOT leave a
        placeholder id like "com.example" as the applicationId.
      - versionCode / versionName: read them from the decompiled apktool.yml
        "versionInfo:" block, then BUMP by one step so the rebuilt APK installs
        as an update over the original
        (PixKudi decompiled: versionCode 5 / versionName 1.0.2  ->  rebuilt:
        versionCode 6 / versionName 1.0.3).
      - The Kotlin source `namespace` (e.g. "com.example") is just the source
        package; only `applicationId` determines the on-device/Play package name.
        Leave the namespace alone (renaming it would need a full source refactor).

1.10 EVERY CHANGE BUMPS THE VERSION. Whenever you modify the app in any way
     (bug fix, UI tweak, feature, string/asset change), increment BOTH the
     versionCode (+1) and versionName (patch +1, e.g. 1.0.3 -> 1.0.4) in
     app/build.gradle.kts BEFORE building, so the new APK always installs as an
     update over the previous one. Keep the user-facing version in sync too:
     res/values/pixkudi_strings.xml <string name="company_version"> and the
     CompanyInfo.version default in data/model/AppConfig.kt (e.g. "Version
     1.0.4" / "1.0.4"). Never ship two different APKs with the same version.

5. KEY IMPLEMENTATION SPECS (behaviour details)
================================================================================

5.1 LOGIN + OTP + APP-NAME GATE
    Flow:
      PhoneStep -> (Next) -> OtpStep -> (auto-fill after 5s) -> confirm -> Home.
    - AuthViewModel: onPhoneNumberChanged (digits, max 11), onAgreeToggled,
      loginOrRegister(onSuccess), clearMessages. Normalize to +234XXXXXXXXXX.
    - Change detection: the confirm path calls userRepository.loginOrRegister()
      which calls customerRepository.loginWithPhone() which queries Supabase.
    - APP-NAME GATE lives in customerRepository.loginWithPhone(): after mapping
      the DTO to the domain model, if
          !customerCase.loanPlatform.trim().equals(<APPNAME>, ignoreCase = true)
      then return Result.failure("This phone number is not registered on <APPNAME>.")
      BEFORE clearing/saving local data. This also guards session restore.
    - OTP AUTO-GEN in the OTP composable:
        LaunchedEffect(step) { if (step == 1) { delay(5000);
          otp = Random.nextInt(0, 10000).toString().padStart(4, '0') } }
      The OTP boxes display `otp`; the confirm button enables when otp.length == 4.
    - On wrong platform: show the error inline, stay on the OTP/login screen, do
      not navigate.

5.2 ANNOUNCEMENT POPUP MODAL (once per hour)
    - Data: Announcement(newsTickerEnabled, newsTickerText, popupModalEnabled,
      popupModalHtml) fetched from brand_settings.
    - Show when: popupModalEnabled == true AND popupModalHtml is not blank AND
      the throttle allows it.
    - Throttle: store "last shown at" epoch millis in SharedPreferences
      (e.g. prefs "announcement_prefs", key "popup_last_shown_at", interval
      60*60*1000 ms). On first ever load it shows; afterwards only if
      now - lastShown >= 1 hour.
    - When shown, mark the timestamp (on dismiss).
    - Trigger point: the authenticated host screen (e.g. MainHostScreen) fires
      LaunchedEffect(Unit) -> mainViewModel.loadAnnouncementAndMaybeShowPopup().
      This runs each time the app opens / host screen is (re)created.
    - UI: a Compose Dialog titled "Announcement", with the HTML rendered inside an
      android.webkit.WebView via AndroidView (loadDataWithBaseURL, JavaScript
      disabled, transparent background, wrapped with a small responsive CSS
      <style> for readable body text and max-width images). A single full-width
      "Okay" button dismisses it. Style header/button with brand theme tokens.
    - Reference: new-pixkudi .../ui/components/AnnouncementPopup.kt and
      data/repository/AnnouncementRepository.kt.

5.3 NEWS TICKER (marquee under the credit card)
    - Text comes from brand_settings.news_ticker_text; render only if
      newsTickerEnabled is true AND text is not blank.
    - Placement: directly under the credit-card panel and above the next panel on
      the Home/dashboard screen.
    - Implementation: an auto-scrolling marquee composable:
        * measure text width with rememberTextMeasurer (softWrap=false, maxLines=1),
        * measure container width with onSizeChanged,
        * animate a float 0..1 with rememberInfiniteTransition +
          infiniteRepeatable(tween(~16000ms, LinearEasing), Restart),
        * offset text by (containerWidth - progress * (containerWidth + textWidth))
          using Modifier.offset { IntOffset(x, 0) } and
          Modifier.wrapContentWidth(unbounded = true) so it is not clipped,
        * put it in a clipped Box with a brand background + brand text color.
    - Style with BRAND THEME TOKENS (no hardcoded colors). Reference:
      new-pixkudi .../ui/components/NewsTicker.kt (uses BrandPrimarySoft bg +
      BrandTextMain text).

5.4 STATE WIRING (repository -> viewmodel -> compose)
